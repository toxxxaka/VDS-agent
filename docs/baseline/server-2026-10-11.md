## Exposure

- Public listeners: SSH 22, HTTP 80, HTTPS 443, WireGuard UDP 51820 and Docker-published TCP 51821.
- Internal listeners include WebUI, MCP and VDS-Agent helpers on loopback.
- IPv6 is enabled; SSH and nginx listen on IPv6. The input policy is drop, with HTTP/HTTPS permitted.
- IPv4 input policy is drop. Docker traffic is handled by Docker chains and `DOCKER-USER`; do not edit Docker-owned nft tables directly.

## SSH effective configuration

- `PermitRootLogin yes` (owner-approved key-only root access)
- `PasswordAuthentication no`; `KbdInteractiveAuthentication no`
- X11, agent and TCP forwarding disabled
- `MaxAuthTries 3`, `MaxSessions 4`, `LoginGraceTime 30`
- Legacy SHA-1 and UMAC-64 MAC entries are still present and require Phase 1 remediation.

## VDS-Agent units

All observed VDS-Agent services and the snapshot timer were active. Current `systemd-analyze security` exposure scores: WebUI 8.4, MCP 7.1, health 5.8, OOM 6.2, infrastructure bridge 8.7, Telegram bot 8.7. These values are the Phase 2 hardening baseline, not a claim of compromise.

## Permissions

Private configuration directories and runtime state are mode 0750. Runtime SQLite data is owned by the monitoring service user. Application source is root-owned and world-readable. Installed VDS-Agent units are root-owned mode 0644. Actual sudoers contents were not copied into this document.

## Caveats

The deployment has two systemd template drifts: the installed infrastructure bridge and SSH-login unit differ from the current repository templates. No deploy was performed during this baseline.
